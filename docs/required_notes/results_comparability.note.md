- **The dashboard's numbers are not these numbers, and the two must not be read against each other.** The console's at-risk and recovered figures come from the API, not from the evaluation harness, and the three definitions that share those names measure different things. `at_risk_amount` is written once when an incident opens, by `at_risk_amount()` in `salvage/detect/incidents.py`, and covers the single 15-minute detection window, counting only orders still unpaid at that instant. `recovered_amount` is recomputed per request and sums every recovery case attached to the incident with outcome RECOVERED, across the incident's whole life, with no restriction to the at-risk set. The at-risk order set in section 1 is a third thing again: every order whose first attempt failed inside a fault window on the fault's instrument, taken from the world's fault schedule over the whole evaluation day and averaged over ten seeds. The API path never consults the fault schedule and the evaluation path never consults the detector. So a dashboard incident showing 20,059 recovered against 21,048 at risk is not a 95 percent recovery rate; it is a numerator spanning about seven times the denominator's window, over a different population. The same applies to the merchant-wide tiles: `stats.recovered_amount` has no time filter at all and counts only the link and steer routes, so it is neither "today" nor comparable to anything in this document. Nothing here is a wrong number. It is three measurement definitions sharing four field names, and the console labels each figure with its scope for that reason.
